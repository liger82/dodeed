# 계획 2 실험 결과 (2부): 로그인 후 최종 확인 화면까지

- 실험일: 2026-11-15
- 1부: [로그인 없이 확인한 예약 자동화](2026-11-15-booking-automation-public.md)
- 방법: 사용자 Mac에 보이는 Chromium 창(Playwright, 모바일 화면)을 띄우고 사용자가 직접 로그인했다. 이후 조작은 같은 브라우저에 붙어서 했다. 비밀번호는 에이전트에 전달되지 않았다.
- 지킨 선: 예약 확정·신청 버튼과 결제 버튼은 누르지 않았다. 자동결제(카드 등록) 권유 팝업은 닫았다. 쿠키 값은 출력하지 않았다. 실험 후 브라우저 프로필, 저장한 로그인 상태, 개인정보가 보이는 스크린샷을 모두 지웠다.

캐치테이블과 네이버 모두 **로그인한 상태로 최종 확인 화면까지** 진행되고, 저장한 로그인 상태를 **새 브라우저에서 다시 쓸 수 있다.** 자동화 차단은 만나지 않았다.

## 결과 요약

| 질문 | 캐치테이블 | 네이버 |
| --- | --- | --- |
| 로그인 후 최종 확인 화면까지 | 됨: 시간 → 좌석 종류 → 추가 상품 → 예약금 안내 → 결제 방식 → 최종 화면(`/ct/reservation/form`) | 됨: 인원 → 날짜 → 시간 → "다음" → 최종 "예약 신청하기" 화면(`…/request/link`) |

| 자동화 탐지·차단 | 없음 | 없음 |
| 간편결제 푸시 | 시험하지 않음 (아래 결정 참고) | 해당 가게는 결제 없음 |

## 결정: 결제 푸시 시험은 하지 않는다

최종 결제 승인은 어차피 사람이 휴대폰에서 한다. 에이전트가 최종 화면까지 가서 내용을 보여 주면 충분하다고 사용자와 합의했다(2026-11-15). 결제 단계의 화면 구성은 실제 결제를 처음 진행할 때 확인한다.

## 설계에 주는 의미

1. **폰 워커(에뮬레이터)는 CBT에 넣지 않는다.** 로그인 후 최종 화면까지 웹으로 된다.
2. **로그인은 사용자가 원격 브라우저에서 직접 하고, 로그인 상태를 저장해 재사용한다.** 저장한 상태는 비밀정보로 다룬다(암호화 보관, LLM에 보내지 않음). 네이버는 만료가 짧을 수 있으므로 만료를 감지하면 사용자에게 다시 로그인을 요청한다.
3. **캐치테이블 최종 화면에 "6분간 예약 찜" 타이머가 있다.** 승인 요청은 최종 화면 도착 즉시 보내야 하고, 승인 전에 시간이 지나면 처음부터 다시 진행한다. 승인 요청에 남은 시간을 표시한다.
4. **금액은 최종 화면에서 읽는다.** 목록과 가게 상세에는 "예약금 0원"으로 표시됐지만 실제 흐름에서는 1인 30,000원, 합계 60,000원 예약금 안내가 나왔다. "0원"은 카드를 등록하고 취소·노쇼 때 수수료를 자동 결제하는 방식이었다. 승인 요청에는 최종 화면의 금액과 취소 수수료 규정(예: 2일 전 무료, 1일 전·당일·노쇼 60,000원)을 그대로 보여 준다.
5. **에이전트는 결제 방식 변경, 카드 등록, 약관 추가 동의를 하지 않는다.** 흐름 중간에 "자동결제" 권유 팝업이 뜨고 기본 선택도 자동결제였다. 이런 선택은 정책 엔진에서 막고 사용자에게 넘긴다.
6. **최종 화면에 사용자 이름과 전화번호가 있다.** 화면 내용을 LLM에 보낼 때 개인정보 가리기를 반드시 거친다(REQ-SEC 출구 필터).
7. **흐름 중간에 추가 상품(꽃다발 등) 단계가 있다.** 에이전트는 추가 상품을 고르지 않고 넘긴다.
8. **네이버는 "확정까지 평균 3시간 이상"을 안내한다.** 1부에서 정한 "신청됨 → 확정 대기 → 확정/거절" 상태와 알림이 필요하다.

## 아직 확인하지 않은 것

- [ ] 결제 단계 화면 구성 (첫 실제 결제 때)
- [ ] 캐치테이블 원격 대기 등록 화면
