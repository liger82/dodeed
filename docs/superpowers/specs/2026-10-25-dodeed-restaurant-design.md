# dodeed 1차 기능 설계: 음식점

- 작성일: 2026-10-25
- 상태: 초안 (승인 대기)
- 선행 문서: [공통 기반 설계](2026-10-25-dodeed-platform-design.md). 표기 규칙([사용자 결정], [Claude 판단], [구현 재량], [확인 필요])과 권한, 보안, 결제 요구사항은 공통 기반 문서를 따른다.

---

## 1. 목적

사용자는 지금 네이버지도와 캐치테이블을 오가며 식당을 고른다. 가려는 곳에서 동선이 괜찮은지, 지금 영업 중인지, 대기가 얼마나 되는지, 예약할 수 있는지, 화장실은 어떤지를 하나하나 확인한다. 게다가 블로그와 네이버 리뷰에는 대가를 받고 쓴 글이 많아서 맛 평가를 믿기 어렵다.

dodeed는 이 확인 과정을 대화 한 번으로 끝내고, 사용자가 고른 식당의 예약이나 대기 등록까지 사용자 이름으로 처리한다.

## 2. 사용자 요청 형태

### REQ-RST-001 상황 기반 요청 [사용자 결정]
dodeed는 다음과 같은 요청을 이해해야 한다.
- 상황: "혼자 간단히 밥 먹기 좋은 곳", "데이트하기 좋은 곳", "가성비 좋은 곳"
- 위치: "강남역 근처", "지금 여기서"(앱 위치), "회사에서 걸어서 10분"
- 시간과 인원: "오늘 7시 2명"
- 조건: 음식 종류, 가격대, "화장실이 매장 안에 있는 곳", "예약 가능한 곳"
- 빠진 조건은 한 번에 하나씩 묻는다. 기본값으로 처리할 수 있는 조건은 묻지 않고, 어떤 기본값을 썼는지 알려준다 [Claude 판단]. 예를 들어 시간을 말하지 않으면 "지금"으로 처리한다.
- 완료 조건: 위 세 가지 상황 표현이 각각 가격대, 좌석 형태, 분위기 키워드 같은 검색 조건으로 바뀌고, 그 조건이 추천 이유에 드러난다.

## 3. 정보 출처

| 정보 | 출처 | 방식 |
|---|---|---|
| 장소 검색, 좌표, 동선(도보·대중교통 시간) | 카카오맵 (k-skill `kakao-map` 참고), 네이버지도 | 공식 API를 우선 쓰고, 안 되면 브라우저로 조회 |
| 영업 시간, 현재 영업 여부 | 네이버지도, 카카오맵 | API 또는 브라우저로 조회 |
| 폐업 여부 | LOCALDATA (k-skill `localdata-business-status` 참고) | 공공 데이터 |
| 실시간 대기, 예약 가능 시간 | 캐치테이블, 네이버 예약 | 브라우저 조작 (필요하면 폰 워커) |
| 블로그 리뷰 | 네이버 블로그 (k-skill `naver-blog-research` 참고) | 검색 API로 찾고 본문 조회 |
| 네이버 방문자 리뷰 | 네이버지도 | 브라우저로 조회 |
| 화장실 정보 | 웹 검색, 블로그, 리뷰 [사용자 결정] | 검색 결과에서 격리 리더가 추출 |
| 카드 결제 데이터 기반 인기도 | BC카드 잇플 (k-skill `bccard-eatpl-search` 참고) | 선택 사항 [Claude 판단] |

- 외부 원문은 모두 격리 리더가 읽고 정해진 스키마로 추출한다 (공통 REQ-SEC-003).
- 각 출처는 상용 이용이 가능한지 확인한 뒤 쓴다 (공통 §7.6).

## 4. 리뷰 구분

### REQ-RST-010 리뷰 분류 [사용자 결정]
리뷰를 다음 세 가지 중 하나로 분류한다.

| 분류 | 판단 근거 | 쓰임 |
|---|---|---|
| 대가성 (협찬, 체험단, 원고료) | 공정위 표시 문구("소정의 원고료", "제품/식사를 제공받아", "체험단", "협찬"), 협찬 배너 이미지의 대체 텍스트와 문구, 체험단 플랫폼 표기 | 가격, 메뉴, 화장실, 주차, 좌석 같은 **정보로만** 쓴다 |
| 내돈내산 | "내돈내산", "직접 결제" 같은 명시적 표현. 네이버 영수증 인증 리뷰도 여기에 넣는다 [Claude 판단] | **정보와 맛 평가**에 모두 쓴다 |
| 불명 | 위 근거가 하나도 없음 | **정보로만** 쓴다 [Claude 판단] |

- 불명 리뷰를 맛 평가에서 뺀 이유: 협찬 리뷰가 맛 평가에 섞이는 것(공통 실패 기준 F5)이 내돈내산 리뷰를 일부 놓치는 것보다 나쁘다 [Claude 판단].
- 맛 평가에 쓸 수 있는 리뷰가 3개 미만이면 점수를 내지 않고 "근거 부족"으로 표시한다 [Claude 판단].
- 맛 평가에는 근거로 쓴 리뷰 수와, 대표 문장의 출처 링크를 함께 보여준다.
- 완료 조건: 협찬 표시 문구가 있는 리뷰를 넣은 테스트 세트에서 맛 평가의 근거로 쓰인 대가성 리뷰가 한 건도 없다. 분류 정확도는 라벨을 붙인 표본 100건 이상으로 측정해 기록한다. 정확도 목표치는 첫 측정 결과를 보고 기획자와 정한다.

## 5. 화장실 정보

### REQ-RST-020 화장실 [사용자 결정]
- 확인 항목은 **남녀 분리 여부**와 **위치(매장 안 / 건물 공용)**다. 청결 상태에 대한 언급이 있으면 함께 확인한다.
- 정보는 웹 검색, 블로그, 리뷰에서 찾는다. 대가성 리뷰도 이런 사실 정보의 출처로는 쓸 수 있다.
- 결과에는 값과 함께 출처와 작성 날짜를 보여준다. 정보를 찾지 못하면 추측하지 않고 "확인 안 됨"으로 표시한다.
- 출처끼리 내용이 다르면 최신 정보를 우선하고, 내용이 엇갈린다는 사실도 함께 표시한다 [Claude 판단].
- 사용자가 화장실이 매장 안에 있는 곳을 원하면, "확인 안 됨"인 식당은 목록에서 빼지 않고 뒤쪽에 표시한다 [Claude 판단].

## 6. 결과 표시

### REQ-RST-030 후보 카드
- 후보 3~5곳 [Claude 판단]을 카드 목록으로 보여준다. 카드마다 다음 항목을 담는다.
  - 이름, 음식 종류, 대표 메뉴와 가격대
  - 동선: 출발 위치에서 걸어서 또는 대중교통으로 걸리는 시간
  - 현재 영업 여부와 영업 종료 시간
  - 대기 상황(대기 팀 수 또는 예상 대기 시간)과 예약 가능 여부
  - 화장실: 남녀 분리 여부, 위치 (출처 날짜 포함)
  - 맛 평가: 내돈내산 리뷰를 바탕으로 한 요약과 근거 리뷰 수, 또는 "근거 부족"
  - 이 상황에 추천하는 이유 한 줄
- 정보마다 조회 시각을 표시한다. 대기 정보는 조회 후 5분이 지나면 "다시 확인 필요"로 표시한다 [Claude 판단].
- 메신저에서는 카드와 버튼(예약, 대기 등록, 지도 보기, 다른 후보)으로 보여주고, 앱에서는 지도와 함께 보여준다 [구현 재량].

## 7. 예약과 대기 등록

### REQ-RST-040 예약 흐름
1. 사용자가 후보를 고르고 날짜, 시간, 인원을 확정한다.
2. 실행 계층이 일회용 작업 공간에서 캐치테이블이나 네이버 예약 페이지를 열고, 사용자 세션으로 예약 직전 단계까지 진행한다.
3. 페이지에서 읽은 실제 값(가게, 일시, 인원, 예약금, 취소 규정)을 보여주며 HITL 승인을 요청한다 (공통 REQ-PERM-002).
4. 사용자가 승인하면 예약을 확정한다. 예약금이 있으면 간편결제의 휴대폰 인증으로 결제한다 (공통 §7.5).
5. 예약 번호와 일시를 사용자에게 알리고 활동 기록에 남긴다.
- 서비스 계정이 연결되지 않았으면 연결 방법을 안내하고, 연결하기 전까지는 조회만 한다.
- 완료 조건: 테스트 계정으로 캐치테이블과 네이버 예약 각각에서 승인, 예약, 알림까지 끝까지 성공한다. 사용자가 승인을 거절하면 아무것도 실행되지 않는다.

### REQ-RST-041 대기 등록 (원격 줄서기)
- 식당이 캐치테이블 등에서 원격 대기를 지원하면 대기를 등록한다. 해당 서비스의 권한 등급이 "바로 실행"이면 승인 없이 등록한다 (공통 REQ-PERM-001).
- 등록 후 대기 순서를 감시하다가, 앞에 남은 팀이 2팀 이하가 되면 알린다 [Claude 판단].

### REQ-RST-042 빈자리 감시
- "토요일 7시에 2명 자리 나면 알려줘" 같은 요청을 감시 작업으로 등록한다 (공통 REQ-BG-001).
- 빈자리가 나면 알리고 예약할지 묻는다. 1차에서는 자동으로 예약하지 않는다 [Claude 판단].

### REQ-RST-043 취소와 변경
- 사용자가 요청하면 HITL 승인을 받은 뒤 예약을 취소하거나 변경한다. 승인 화면에는 취소 수수료와 예약금 환불 규정을 보여준다.

## 8. 위치

- 앱 사용자가 "지금 여기서"라고 하면 앱이 보낸 현재 위치를 쓴다.
- 메신저만 쓰는 사용자에게는 지명을 묻거나, 텔레그램 위치 공유(1회)를 요청한다 [Claude 판단].
- LLM에는 근처 지명만 전달하고, 동선 계산은 서버의 도구가 실제 좌표로 한다 (공통 REQ-SEC-002).

## 9. 개인화 연계 (개인화를 켠 사용자)
- 상황별 선호(혼밥 가격대, 화장실 선호, 자주 가는 지역)를 기본 조건으로 쓰고, 어떤 선호를 반영했는지 결과에 한 줄로 밝힌다.
- 다녀온 식당과 사용자가 고른 후보를 기록한다 (공통 REQ-PER-002).

## 10. 1차 출시 완료 기준
- REQ-RST-001부터 REQ-RST-043까지의 완료 조건 통과
- 공통 기반 문서의 REQ-ACC, REQ-CHN, REQ-PERM, REQ-EXE, REQ-SEC, REQ-BG, REQ-PER 완료 조건 통과
- 인젝션 테스트 세트(리뷰와 예약 페이지에 숨긴 지시문)에서 승인되지 않은 실행이 한 건도 없음
- 공통 §7.3 실험 결과를 문서로 남기고, 폰 워커 포함 여부 결정
- 법률 검토(공통 REQ-SEC-009) 완료

## 11. 검증 환경 [Claude 판단]
- 자동화 테스트는 캐치테이블과 네이버 예약 화면을 본뜬 **모의 사이트**에서 한다. 모의 사이트에는 인젝션 문구를 넣은 페이지와 화면 구조를 바꾼 페이지도 포함한다.
- 실제 사이트는 기획자 계정으로 직접 점검(smoke test)한다. 예약금이 없는 식당에 예약한 뒤 바로 취소하는 방식으로 하고, 점검 횟수는 최소한으로 줄인다. 노쇼 제재를 피하려면 예약 시간보다 충분히 앞서 취소한다.
- REQ-RST-040의 "끝까지 성공" 조건은 모의 사이트 자동화 테스트 통과와 실제 사이트 점검 기록, 두 가지를 모두 갖추면 충족된다.

## 12. 구현 재량
- 카드 UI의 세부 디자인
- 출처별 수집 순서와 캐시 정책 (단, 대기 정보의 신선도 기준은 지킨다)
- 리뷰 분류 구현 방식 (규칙 기반, LLM 분류, 둘의 혼합)
