## 1. 배경과 목적

기획자는 오픈소스 개인 에이전트 Hermes Agent(Nous Research)의 장점을 dodeed에 가져오기로 했다. **Hermes 코드를 쓰지 않고, 장점만 dodeed 보안 구조 안에 다시 만든다** [사용자 결정].

가져올 장점은 두 가지다 [사용자 결정].
1. **기억과 스킬**: 대화 내용을 기억하고 사용자의 선호를 메모해 둔다. 복잡한 작업의 절차를 스킬로 저장해 두었다가, 같은 종류의 작업이 들어오면 빠르게 처리한다.
2. **스케줄 실행**: 정해진 시간에 작업을 반복해서 실행한다.

Hermes는 한 사람이 자기 서버에서 쓰는 개인 비서다. 그래서 에이전트가 대화와 웹 내용을 보고 기억과 스킬을 직접 써 넣는다. dodeed는 여러 사용자가 쓰는 서비스이고, 웹 원문이 결정하는 AI에 닿지 않도록 설계했다(REQ-SEC-003). 이 원칙을 지키려면 기억과 스킬이 **사용자 자신의 말과 사용자가 승인한 행동에서만** 만들어져야 한다.

## 2. 목표, 범위 제외, 실패 기준

### 목표
- M1. 지난 대화에서 한 말을 다음 대화에서 다시 꺼내 쓴다. 예: "지난번에 간 그 국밥집".
- M2. 사용자의 선호를 메모로 조용히 기억하고, 다음 요청에 기본 조건으로 쓴다. 사용자는 메모를 보고 고칠 수 있다.
- M3. 복잡한 작업을 한 번 해낸 뒤 그 절차를 스킬로 저장할지 사용자에게 묻는다. 저장된 스킬은 같은 종류의 요청이 들어오면 묻고 찾는 과정을 건너뛰고 바로 실행한다.
- M4. 사용자가 정한 시간에 작업을 반복 실행한다. 결과를 처리하는 방식은 사용자가 스케줄마다 고른다.

### 범위 제외
- Hermes Agent 코드나 패키지 도입 [사용자 결정]
- 모델 학습(파인튜닝)과 사용자 데이터를 이용한 학습. 선호는 메모로 저장할 뿐 학습하지 않는다 [사용자 결정].
- 에이전트가 스스로 새 도구나 코드를 만드는 것
- 사용자 간 스킬 공유
- 에이전트가 터미널이나 임의 코드를 실행하는 것

### 실패 기준 (기능이 동작해도 실패로 보는 경우)
- F6. 웹페이지, 리뷰, 검색 결과 같은 외부 원문이 기억, 선호 메모, 스킬에 들어간다.
- F7. 사용자가 승인하지 않은 스킬이 저장되거나 실행된다.
- F8. 스케줄 실행이 사용자 승인 없이 예약을 확정하거나 결제한다.
- F9. 개인화를 끈 사용자의 기억, 선호 메모, 스킬이 저장되거나 쓰인다.
- F10. 한 사용자의 기억이나 스킬이 다른 사용자의 대화에 나타난다.

공통 기반 문서의 실패 기준 F1~F5도 그대로 적용된다.

## 3. 출시 범위와 일정

- 기억, 선호 메모, 스킬, 스케줄 실행을 모두 **12월 전 CBT에 포함한다** [사용자 결정].
- 스케줄의 "예약 진행 후 확정만 승인" 모드(§6.2)는 계획 3의 예약 기능이 있어야 동작한다. 계획 3이 늦어지면 그 모드만 "알림까지만"으로 제한해서 출시한다 [Claude 판단].
- 구현 위치 [Claude 판단]: 계획 4(감시, 개인화, 앱)에 기억·스킬·스케줄 작업을 합친다. LLM 공급자 연결(§8)은 계획 4보다 먼저, 독립 작업으로 진행한다.
- **대기 동작(pending action) 서비스**는 계획 3의 HITL 승인과 이 문서의 스킬 저장·스케줄 확인이 함께 쓰는 공통 기반이다. 계획 3의 첫 작업으로 한 번만 만들고, 이 문서의 기능은 그것을 재사용한다 [Claude 판단]. 같은 기능이 두 벌 생기지 않게 하기 위해서다.
- 가입 연령 확인은 CBT에서는 **자기 신고**(만 18세 이상 확인 체크)로 한다 [Claude 판단]. 참가자 20명 미만의 초대제라서다. 정식 출시 전에 본인인증 필요 여부를 법률 검토와 함께 다시 정한다.

## 4. 기억

### REQ-MEM-001 적용 대상
- 기억, 선호 메모, 스킬은 **개인화를 켠 사용자에게만** 동작한다 (REQ-PER-001). 개인화를 끄면 새로 저장하지 않고 기존 내용도 쓰지 않는다. 기존 내용을 지울지는 따로 묻는다.
- **스케줄은 개인화와 무관하게 동작한다** [Claude 판단]. 스케줄은 사용자가 명시적으로 지시한 작업이지 기억이 아니기 때문이다. 그래서 스케줄은 만들 때 실행 내용(스킬 또는 요청 템플릿)을 **복사해서** 저장하고, 원래 스킬을 참조하지 않는다. 개인화를 끄거나 스킬을 지워도 스케줄은 그대로 돈다.
- 완료 조건: 개인화를 끈 사용자에 대해 기억·메모·스킬 관련 도구가 정책 엔진에서 거부된다. 같은 사용자의 스케줄은 계속 실행된다.

### REQ-MEM-002 대화 회상
- 대화가 끝나면(마지막 메시지 후 [Claude 판단: 30분] 동안 새 메시지가 없으면) 그 대화의 요약을 만들어 저장한다.
  - 요약 대상은 이미 가명 처리된 대화 이력(사용자 발화와 최종 답변)뿐이다. 도구 결과와 외부 원문은 대상이 아니다 (REQ-SEC-003, R42).
  - 요약은 [Claude 판단: 300자] 이내다.
- 오케스트레이터는 `recall_conversations(query)` 도구로 **그 사용자 자신의** 지난 대화 요약을 검색한다. 결과는 최근 순 [Claude 판단: 최대 5건]이다.
- 검색 방식은 구현자가 정한다 [구현 재량]. PostgreSQL 전문 검색이나 트라이그램 검색으로 충분하다.
- 완료 조건: 다른 사용자의 요약이 검색 결과에 한 건도 나오지 않는다. 요약 생성 입력에 도구 결과 문자열이 포함되지 않는다.

### REQ-MEM-003 선호 메모
- 사용자마다 선호 메모 하나를 둔다. 메모는 **항목 목록**이다: `{주제, 내용, 근거 대화, 갱신 시각}`. 예: `{주제: "혼밥 가격대", 내용: "1만 원 안팎"}`.
- 전체 크기는 [Claude 판단: 1,500자] 이내다. 넘으면 오래되거나 덜 쓰인 항목부터 합치거나 지우도록 오케스트레이터에 정리를 요청한다.
- 저장 방식: 오케스트레이터가 사용자 발화나 사용자의 선택(후보 선택, 예약 승인)에서 선호를 알아채면 `remember_preference(topic, content)` 도구를 호출한다. 사용자에게 묻지 않고 조용히 저장한다 [사용자 결정].
- 입력 검증 [Claude 판단]:
  - `topic`은 40자, `content`는 120자 이내다.
  - URL, 이메일, 전화번호 패턴, 꺾쇠괄호(`<`, `>`)가 들어 있으면 거부한다.
  - 지시문처럼 보이는 표현("무시하고", "항상 ~하라", "시스템")이 들어 있으면 거부한다. 표현 목록은 구현 재량이다.
- 사용자는 앱, 웹, 메신저에서 메모를 보고, 고치고, 지울 수 있다 [사용자 결정]. 메신저에서는 "내 메모 보여줘", "혼밥 가격대 메모 지워줘"처럼 말로 한다.
- LLM에는 메모 내용을 시스템 메시지로 넘긴다. 넘기기 전에 가명 처리(REQ-SEC-002)를 한다.
- 완료 조건:
  - 인젝션 테스트 세트(REQ-SEC-003)의 문장이 어떤 경로로도 메모에 저장되지 않는다.
  - 검증 규칙을 어긴 입력은 저장되지 않는다.
  - 사용자가 지운 항목은 다음 대화부터 쓰이지 않는다.

## 5. 스킬

### REQ-SKL-001 스킬의 형태
- 스킬은 자유 문장이 아니라 **정해진 형식의 절차**다 [Claude 판단]:
  ```
  이름: "금요일 저녁 데이트 식당"
  설명: 언제 쓰는 스킬인지 한 문장
  단계: [
    { 도구: "search_restaurants",
      고정 인자: { situation: "date", area_query: "강남역", party_size: 2 },
      변수 인자: ["time_text"] }
  ]
  ```
- 결과 처리 방식(`notify_only` / `reserve_then_confirm`)은 **스킬이 아니라 스케줄에만** 둔다 [Claude 판단]. 대화 중에 스킬을 실행하면 항상 후보 카드를 보여주고, 예약은 지금처럼 사용자가 고른 뒤 진행한다. LLM의 도구 호출 하나가 예약 흐름을 시작하는 경로를 만들지 않기 위해서다.
- 단계의 도구는 도구 레지스트리에 등록된 것만 쓸 수 있다. 쓰기·실행 도구가 들어가도 실행할 때는 정책 엔진과 HITL을 그대로 거친다 (REQ-PERM-001, 002).
- 고정 인자와 설명에는 선호 메모와 같은 입력 검증(REQ-MEM-003)을 적용한다.
- 스킬은 사용자마다 따로 저장한다. [Claude 판단: 사용자당 최대 20개]

### REQ-SKL-002 스킬 저장 제안
- 다음 경우에 오케스트레이터는 그 절차를 스킬로 저장할지 **사용자에게 묻는다** [사용자 결정]:
  - 같은 종류의 요청을 [Claude 판단: 2번째] 처리했을 때 (같은 도구, 비슷한 고정 인자)
  - 도구를 [Claude 판단: 2단계 이상] 거친 작업을 끝냈을 때
- 제안 메시지에는 스킬 내용(이름, 단계, 고정 인자)을 보여주고 "저장 / 고쳐서 저장 / 안 함" 버튼을 붙인다. 내용은 LLM이 쓴 문장이 아니라 서버가 스킬 구조에서 만든다 (REQ-PERM-002와 같은 원칙).
- 제안은 **대기 동작(pending action)**으로 서버에 저장한다 [Claude 판단]. 버튼의 payload는 대기 동작의 일회용 식별자이고, 게이트웨이가 가로채 서버가 직접 처리한다. 버튼 payload는 LLM에 텍스트로 넘기지 않는다. 대기 동작은 [Claude 판단: 24시간] 뒤 만료된다.
- "고쳐서 저장"을 누르면 사용자가 말로 고칠 내용을 알려준다. 오케스트레이터가 수정한 제안을 다시 만들면, 서버가 다시 보여주고 새 버튼을 붙인다. 수정본에도 입력 검증(REQ-MEM-003)과 출처 검사(REQ-SEC-010)를 다시 적용한다 [Claude 판단].
- "안 함"을 고르면 같은 종류는 [Claude 판단: 30일] 동안 다시 묻지 않는다.
- 완료 조건: 사용자가 "저장"을 누르지 않은 스킬은 저장되지 않는다.

### REQ-SKL-003 스킬 실행
- 사용자의 요청이 저장된 스킬과 맞으면 오케스트레이터는 `run_skill(skill_id, 변수 인자)` 도구를 호출한다. 모르는 변수 인자만 묻고 나머지 질문은 건너뛴다.
- 실행 결과에는 어떤 스킬을 썼는지 한 줄로 밝힌다. 예: "저장된 '금요일 저녁 데이트 식당' 절차로 찾았어요."
- 완료 조건: 스킬로 실행한 검색이 사용자가 직접 요청한 검색과 같은 정책 검사, 감사 기록, 카드 형식을 거친다.

### REQ-SKL-004 스킬 관리
- 사용자는 앱, 웹, 메신저에서 스킬 목록을 보고, 이름과 고정 인자를 고치고, 지울 수 있다.
- 오케스트레이터가 스킬 수정을 제안할 때도 REQ-SKL-002처럼 사용자 승인을 받는다.

## 6. 스케줄 실행

### REQ-SCH-001 스케줄 만들기
- 사용자가 대화로 반복 실행을 요청하면 스케줄을 만든다. 예: "매주 금요일 오후 5시에 오늘 저녁 데이트 식당 찾아줘".
- 스케줄은 `{반복 규칙(KST), 실행할 스킬 또는 요청 템플릿, 결과 처리 방식, 다음 실행 시각}`으로 저장한다. 요청 템플릿도 스킬과 같은 형식이다 (REQ-SKL-001).
- 만들기 전에 반복 규칙과 실행 내용을 서버가 만든 문장으로 보여주고 확인을 받는다. 확인은 스킬 저장과 같은 대기 동작 방식(REQ-SKL-002)으로 처리한다.
- 실행 내용은 만들 때 복사해서 저장한다 (REQ-MEM-001). 변수 인자(예: 날짜)는 실행할 때 실행 시각 기준으로 채운다 [Claude 판단].
- 개수 제한은 구독 등급 설정값을 따른다 (공통 §12). [Claude 판단: CBT 기본값 사용자당 5개]
- 반복 규칙 표현 방식은 구현자가 정한다 [구현 재량]. 매일, 요일, 특정 시각 정도면 충분하다.

### REQ-SCH-002 결과 처리 방식 [사용자 결정]
스케줄마다 사용자가 고른다.

| 방식 | 동작 |
|---|---|
| 알림까지만 (`notify_only`) | 실행 결과(후보 카드)를 알림으로 보내고 멈춘다 |
| 예약 진행 후 확정만 승인 (`reserve_then_confirm`) | 1순위 후보로 예약 직전 단계까지 진행한 뒤, 확정 승인 요청(REQ-PERM-002)을 보낸다. 사용자가 승인하면 확정하고, 결제가 필요하면 간편결제 휴대폰 인증을 거친다 |

- 어떤 방식이든 **확정과 결제는 사용자 승인 없이 일어나지 않는다**.
- 승인 요청이 만료되면(10분) 예약 직전 상태를 버리고 "승인 시간이 지나 예약을 진행하지 않았어요"라고 알린다.
- 1순위 후보로 예약할 수 없으면 다음 후보로 [Claude 판단: 최대 2번] 더 시도한 뒤 알림으로 바꾼다.

### REQ-SCH-003 실행과 실패
- 스케줄은 공통 기반의 스케줄러(REQ-BG-001)로 실행한다. 앱과 메신저가 꺼져 있어도 돈다.
- 실행에 쓰는 대화는 사용자의 대화 세션과 이어진다.
- 결과 알림과 승인 요청은 **먼저 알릴 수 있는 채널**로 보낸다 [Claude 판단]: 텔레그램이 연결돼 있으면 텔레그램, 없으면 dodeed 앱 푸시다. 웹은 요청이 와야 답하는 채널이라 웹 화면의 알림함에만 남긴다.
- `reserve_then_confirm` 스케줄은 텔레그램이나 앱 푸시가 연결된 사용자만 만들 수 있다 [Claude 판단]. 웹만 쓰는 사용자는 승인 요청 10분 안에 알림을 받을 방법이 없기 때문이다.
- 로그인 세션이 만료됐거나 외부 서비스가 실패하면 그 회차를 건너뛰고 이유를 알린다. [Claude 판단: 3회 연속 실패하면 스케줄을 일시정지하고 알린다]
- 사용자는 스케줄을 보고, 일시정지하고, 지울 수 있다.
- 완료 조건: `reserve_then_confirm` 스케줄을 실행해도 승인 토큰 없이는 확정 동작이 일어나지 않는다 (REQ-EXE-001 테스트를 스케줄 경로에도 적용).

## 7. 보안 요구사항 (추가)

### REQ-SEC-010 기억과 스킬의 출처
- 기억, 선호 메모, 스킬은 **사용자 발화, 사용자의 선택, 사용자가 승인한 행동**에서만 만든다.
- 격리 리더의 출력과 도구 결과 문자열은 이 도구들의 입력으로 쓸 수 없다.
- 검사 방식은 **"외부 문자열을 막는" 방식이 아니라 "출처를 증명하는" 방식**으로 한다 [Claude 판단]. 메모 내용, 스킬의 설명과 고정 인자의 문자열 값은 다음 중 하나여야 저장된다.
  1. **사용자 발화에서 온 값**: 그 사용자의 최근 [Claude 판단: 30개] 발화(가명 처리 전 원문) 중 하나에 그대로 들어 있는 문자열. 정규화(공백, 대소문자) 후 비교한다.
  2. **서버가 확인한 장소 참조**: 사용자가 고르거나 예약한 후보의 장소 식별자(`place_id`). 이때 저장하는 이름은 LLM이 쓴 값이 아니라 서버가 그 식별자로 찾은 값이다. 예: "단골: ○○국밥집".
  3. **정해진 값 목록에 있는 값**: 상황 종류, 가격 같은 열거형과 숫자 필드.
- 짧은 연결 표현(조사, "안팎", "이하" 등)은 출처 검사에서 제외하되 [Claude 판단: 전체 길이의 30% 이하]만 허용한다. 구체 규칙은 구현 재량이다.
- 대화 요약(REQ-MEM-002)과 회상 결과는 출처로 인정하지 않는다. 요약은 LLM이 만든 문장이라서다.
- 완료 조건:
  - 인젝션 테스트 세트를 블로그 본문과 리뷰에 넣고 대화를 진행해도 메모, 스킬, 스케줄에 해당 문장이 저장되지 않는다.
  - "아까 두 번째 집 기억해 둬"는 장소 참조(2번)로 저장되고, 그 장소 이름은 서버 데이터와 같다.

### REQ-SEC-011 사용자 간 분리
- 기억, 메모, 스킬, 스케줄은 모든 조회와 실행에서 사용자 식별자로 범위를 제한한다.
- 완료 조건: 두 사용자의 데이터를 만든 뒤 교차 조회 테스트에서 상대 데이터가 한 건도 나오지 않는다.

### REQ-SEC-012 기록과 삭제
- 메모, 스킬, 스케줄의 생성, 변경, 삭제는 모두 감사 로그에 남긴다 (REQ-SEC-007). 감사 로그 detail에는 내용 본문을 넣지 않고 종류와 식별자만 넣는다.
- 사용자가 개인화 기록 삭제를 요청하면 대화 요약, 선호 메모, 스킬을 즉시 지운다. 스케줄은 개인화 기록이 아니므로 지우지 않고, 따로 지울지 묻는다 [Claude 판단]. 탈퇴하면 스케줄까지 모두 지운다.

## 8. LLM 공급자 [사용자 결정]

- 1차 모델: **gpt-6-luna** (OpenAI API 직접 연결)
- 백업 모델: **gemini-3.5-flash-lite** (Gemini API 직접 연결, **결제 등급만** 사용)
- 선정 이유: 가격과 추론 성능 점수 [사용자 결정]
- OpenRouter 같은 중개 서비스는 쓰지 않는다. 데이터를 받는 회사가 하나 늘고 수수료가 붙기 때문이다 [사용자 결정].
- 전환 규칙 [Claude 판단]: 1차 모델이 시간 초과, 429, 5xx, 연결 오류를 내면 그 호출만 백업 모델로 다시 보낸다. 출구 필터(GuardedLLM)는 전환 바깥에서 한 번 거친다. 대화 기록은 공급자 중립 형식이라 중간에 모델이 바뀌어도 이어진다.
- OpenAI 호출은 Chat Completions API를 쓰고 항상 `store=false`로 보낸다 [Claude 판단].
- 두 API 키는 설정값(`DODEED_OPENAI_API_KEY`, `DODEED_GEMINI_API_KEY`)으로 받고 출구 필터에 비밀값으로 등록한다. 모델 이름도 설정값으로 둔다.
- 한국어 품질 확인 [Claude 판단]: CBT 전에 한국어 식당 요청 20~30개로 두 모델의 도구 호출 정확도를 비교하고 결과를 기록한다.

### REQ-SEC-008 개정 [사용자 결정]
공통 기반 문서의 REQ-SEC-008을 다음으로 바꾼다.
- **CBT**: LLM 공급자는 사용자 데이터를 **학습에 쓰지 않아야** 한다. 남용 감시용 보관(OpenAI 최대 30일, Gemini 결제 등급의 제한된 기간)은 허용하고, 이 내용을 개인정보 처리방침과 가입 시 국외 이전 동의에 공개한다.
- **정식 출시 전**: OpenAI 데이터 무보관(ZDR) 신청과 Gemini의 Vertex AI 전환을 다시 검토한다.

### 공급자 약관에 따른 조건 [확인 필요]
- Gemini API 약관은 18세 미만이 쓸 수 있는 앱에서의 사용을 금지한다. 그래서 dodeed 가입은 만 18세 이상으로 제한한다 [Claude 판단]. 가입 화면의 연령 확인 방식은 계획 4에서 정한다.
